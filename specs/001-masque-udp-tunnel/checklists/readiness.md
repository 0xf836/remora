## Requirement Clarity

- [ ] CHK006 Are cancellable pending data, transmission commitment and kernel/network in-flight traffic explicitly distinguished, including the observable limits of cancellation after each boundary? [Clarity, Spec §FR-010/014; Spec §Clarifications; Plan §Transmission commitment and session closure (R1); ADR-0001 §Transmission commitment and close (independent review R1)]
- [ ] CHK007 Is an accepted or Active session explicitly distinguished from proven destination responsiveness and successful application delivery? [Clarity, Spec §FR-022; Data Model §Connection state machine; Wire §Request and acceptance]
- [ ] CHK008 Are application session inactivity, transport liveness and reclamation of already closed resources defined as separate periods, with clear activity sources and reasons for any shorter idle-timeout override? [Clarity, Spec §FR-012/014; Spec §SC-006/007; Config §Optional sections and documented initial defaults; Amendments §R4]
- [ ] CHK009 Are permanent rejection, operator action and transient recovery defined precisely enough to explain why flow cleanup or a new local sender does not resume permanently denied setup? [Clarity, Spec §FR-019; Data Model §Session state machine; Config §Updates and failure contract]
- [ ] CHK010 Are offered, accepted, transmitted and delivered traffic measurements distinguished from local drops, kernel drops and estimated outer-transport loss? [Clarity, Spec §FR-021/022/027; Diagnostics §Required measurements and meanings; Benchmarks §Reference topology and workload]

## Requirement Consistency

- [ ] CHK011 Do the A1 isolation requirements consistently preserve mandatory client/session separation while documenting indistinguishable external UDP replies without prescribing a fixed quarantine mechanism? [Consistency, Spec §FR-010/014; Spec §Assumptions; Amendments §A1; ADR-0001 §Isolation design and reuse trade-offs]
- [ ] CHK012 Are the closure requirements consistent across the specification, lifecycle model and output contract about cancellable discard, original-association completion, unchanged output deadlines and the protection of unrelated sessions? [Consistency, Spec §FR-010/013/014; Data Model §Validation and invariants; Plan §Transmission commitment and session closure (R1); Amendments §R1]
- [ ] CHK013 Are successful response requirements explicit and mutually consistent about forbidden Capsule statuses 204/205/206, prohibited message fields and malformed-message outcomes before forward eligibility? [Consistency, Spec §FR-002/008; Wire §Request and acceptance; Amendments §R2]
- [ ] CHK014 Do Capsule requirements consistently retain mandatory structure, Context ID, size and truncation checks before discarding a valid unsupported carrier, while preserving the unreliable-only scope? [Consistency, Spec §FR-002/005/016; Wire §Capsule and stream lifecycle; Amendments §R3]
- [ ] CHK015 Are SC-010 correlation obligations reconciled with ordinary event suppression, terminal cleanup, bounded status retention and failed output without treating lost diagnostic coverage as a pass? [Consistency, Spec §FR-022/023; Spec §SC-010/Assumptions; Diagnostics §Terminal failure correlation and collection limits (R5); Amendments §R5]
